# WITW 파이프라인 EC2 장애 실험 결과

EC2 3대에서 장애 주입, 개선 전·후 비교, 최종 데이터 대조를 완료했다.
Collector 전송 전 종료의 유실, 중복 이벤트의 반복 쓰기, 순서 역전의 잘못된 연결이 개선됐다.
반면 1만 건 처리 시험에서 개선 버전의 지연은 증가했다. 신뢰성 개선과 지연 비용을 함께 기록한다.

## 실행 환경과 범위

| 항목 | 실제 구성 |
|---|---|
| 실행 ID | `witw-rel-20261123-105044-35b97a` |
| 날짜 | 2026-11-23, 서울 리전, 동일 가용 영역 |
| EC2 | `m7i.xlarge` 3대, 각 4 vCPU·16GiB |
| 디스크 | 각 gp3 100GiB, 기본 3,000 IOPS·125MiB/s |
| infra 노드 | Kafka, PostgreSQL, Redis, Kafka exporter |
| compute 노드 | Collector, 고정 NLP 결과 재생, Spark `local[2]`, Toxiproxy, 실험 제어기 |
| app 노드 | 개선 전·후 Backend, Prometheus, Alertmanager, 웹훅 수신기, Grafana |
| 외부 LLM | 호출하지 않음. 고정 결과를 사용하되 Kafka 전달·소비는 실제 실행 |
| 인스턴스 최초 시작 | 2026-11-23 20:07:24~31 KST |
| 결과 회수·리소스 정리 완료 | 2026-11-23 22:49:56 KST |

예정한 8시간은 실행 상한이었다. 시나리오가 먼저 끝나 약 2시간 43분 안에 결과 회수와 정리를 완료했다.
8시간 연속 부하 시험을 수행한 것은 아니다.

정식 실행은 핵심 시험 27회, Kafka·Spark 추가 시험 6회, 1만 건 처리 시험 6회,
노드 중지·시작 9회다. 별도로 장시간 TCP 차단과 발생·복구 웹훅을 1회 검증했다.
반복 대상 장애는 각각 3회 실행했고, 처리 시험은 개선 전·후 각각 3회 실행했다.
정식 입력 집계는 96,106건이다: 핵심 21,106 + 추가 6,000 + 처리 시험 60,000 + 노드 시험 9,000.
추가 시험의 검증기가 재확인한 장시간 차단 입력 100건은 중복 합산하지 않았다.
중단된 추가 시험의 입력은 정식 합계에서 제외했다.

## STAR

**상황:** 수집 시점과 Kafka 전송, Kafka 재전달과 DB 커밋 사이의 경계에서
유실·중복 쓰기가 발생할 수 있었다. 관련 이벤트의 도착 순서도 보장되지 않았다.

**과제:** 로컬에서 관측한 개선이 분리된 EC2 노드에서도 유지되는지,
프로세스 종료·의존 서비스 중단·호스트 재시작 후 데이터가 복구되는지 확인한다.

**행동:** Collector의 영속 outbox, 안정적인 이벤트 ID, Backend inbox와 트랜잭션,
의존 이벤트 재처리를 적용했다. 지정한 실행 지점에서 SIGKILL을 주입하고,
입력 manifest, Kafka의 실제 레코드, DB 최종 상태를 별도로 대조했다.
Prometheus 규칙 → Alertmanager → 실제 HTTP 수신기 경로도 검증했다.

**결과:** 아래 장애 조건에서 유실과 잘못된 연결을 재현하고 개선 효과를 확인했다.
재전달 자체는 남았으며, 개선 버전의 처리 지연 증가도 관측했다.

## 핵심 장애 비교

아래 값은 특별한 표기가 없으면 3회 합계다.

| 시나리오 | 개선 전 | 개선 후 |
|---|---:|---:|
| Collector 전송 전 종료, 각 1,000건 × 3회 | 3건 유실 | 0건 유실 |
| 이슈 이벤트 20% 중복 주입 | 이슈 쓰기 360회 | 이슈 쓰기 300회 |
| 의존 이벤트 순서 역전, 1,000건 × 3회 | 잘못되거나 누락된 연결 3,000건 | 잘못된 연결 0건 |
| DB 커밋 후 offset 커밋 전 종료 | 이슈 쓰기 6회 | 이슈 쓰기 3회 |
| DB 커밋 전 종료 | 재전달 후 쓰기 3회 | 재전달 후 쓰기 3회 |
| PostgreSQL 약 42초 정지, 1,000건 × 3회 | 최종 유실 0건 | 최종 유실 0건 |

PostgreSQL 복구 후 drain은 14.60~15.39초였다.
Collector 개선 버전의 ACK 후 outbox 삭제 전 종료에서는 Kafka에 물리적 중복이
175·188·180건, 합계 543건 발생했으나 최종 데이터는 올바르게 수렴했다.
이는 재전달을 허용하고 최종 반영을 멱등하게 만드는 동작의 검증이다.

검증기는 article ID, 불필요한 추가 ID, 내용, 최종 연결, raw 본문 해시를 대조했다.
핵심 시험 전체를 개선 Backend 기준으로만 합산하면 missing 3건이 남는다.
이 3건은 **구버전 Collector를 의도적으로 실행한 비교군에서 Kafka에 도착하지 않은 입력**이다.
Backend 개선으로 이미 유실된 상류 입력을 복구했다는 의미로 해석하지 않는다.
개선 Collector 시험에서는 해당 유실이 없었다.

## Kafka·Spark 추가 시험

| 장애 | 반복 | 입력 | 장애 주입 → 복구 관측 |
|---|---:|---:|---:|
| Kafka 30초 중단 | 3회 | 각 1,000건 | 47.15 / 55.21 / 46.78초 |
| Spark 일부 출력 후 SIGKILL | 3회 | 각 1,000건 | 66.92 / 71.00 / 68.87초 |

각 시험에서 개선 전·후 Backend 모두 입력 1,000건이 최종 저장됐고,
누락·추가 ID·내용 오류·연결 오류는 0건이었다.
Spark 종료 시점에는 체크포인트에 아직 커밋되지 않은 입력 1,000건이 존재함을 확인했다.

첫 추가 시험 실행(`20261123T114819Z`)에서는 Kafka 재시작 후 검증기의
AdminClient가 오래된 leader epoch를 사용해 `FENCED_LEADER_EPOCH`와 대기 timeout이 발생했다.
새 AdminClient로 데이터 저장과 offset을 확인한 뒤 관측기를 수정하고 6회를 다시 수행했다.
실패한 실행과 진단 자료도 보존했으며, 정식 완료 결과는 재실행 `20261123T115819Z`다.

## EC2 노드 중지·시작

각 시험 전에 outbox에 1,000건을 보관했다. 노드별 3회, 총 9회 모두
Kafka 고유 입력 1,000건, 양쪽 Backend 최종 저장 1,000건,
누락·추가 ID·내용·연결 오류 0건으로 통과했다.

| 중지 대상 | 1회차 | 2회차 | 3회차 |
|---|---:|---:|---:|
| infra | 706.78초 | 678.25초 | 681.02초 |
| app | 130.49초 | 135.67초 | 138.01초 |
| compute | 117.04초 | 117.77초 | 121.78초 |

시간은 외부 제어기의 EC2 중지 요청부터 데이터 대조 완료까지다.
중지·기동, Collector의 600초 재시도 주기, drain, 검증 시간이 포함된다.
따라서 순수 서비스 복구 시간이나 운영 MTTR로 쓰지 않는다.
실제 EC2 stop/start이며, 강제 전원 차단이나 디스크 소실 실험은 아니다.

## 1만 건 처리 시험: 정확성 통과, 지연 증가

개선 전·후 Backend를 하나씩 활성화하고 `전→후 / 후→전 / 전→후` 순서로 실행했다.
각 실행은 10,000건, 20개 주제, 주제별 이슈 후보 20개, 768차원 벡터를 사용했다.
6회 모두 저장 10,000건, 누락·추가·내용·연결 오류 0건이었다.

| 실행 | 버전 | p95 지연 | 배치 완료 환산 처리량 |
|---|---|---:|---:|
| soak-120500 | 전 | 209.31초 | 46.98건/초 |
| soak-121333 | 후 | 296.36초 | 33.18건/초 |
| soak-122227 | 후 | 287.23초 | 33.86건/초 |
| soak-123110 | 전 | 219.82초 | 44.77건/초 |
| soak-123955 | 전 | 221.83초 | 44.37건/초 |
| soak-124837 | 후 | 286.83초 | 34.26건/초 |

실행별 p95의 산술평균은 216.99 → 290.14초로 약 33.7% 증가했다.
전체 표본을 합친 p95가 아니며, 성능 개선의 근거로 사용할 수 없다.
지연은 Collector discovery 시각부터 PostgreSQL에서 커밋된 최종 연결을 처음 관측할 때까지다.
입력 staging·대기열·0.5초 SQL 관측 주기가 포함된다.
처리량은 `10,000 / 마지막 도착 지연`이므로 지속 TPS나 최대 처리 용량을 뜻하지 않는다.

첫 개선 전 실행 중 모니터링 이력 추출과 증거 백업이 compute 노드의 자원을 함께 사용했다.
실행별 자원 경합을 완전히 통제한 성능 비교가 아니므로 지연 증가의 원인을
inbox 등 특정 구현으로 단정하거나 일반적인 성능 저하율로 확대하지 않는다.
동일 부하에서의 추가 지연 분석과 최적화가 후속 과제다.

## 장애 알림과 관측

장시간 TCP 차단에서 운영 설정을 유지했다: outbox 대기 900초 초과,
`for: 2분`, scrape/evaluation 15초, Alertmanager group_wait 30초.

| 항목 | 실측 |
|---|---:|
| 장애 → firing 웹훅 독립 관측 | 1,071.005초 |
| TCP 복구 → outbox 100건 ACK 완료 | 128.430초 |
| outbox 해소 → resolved 웹훅 독립 관측 | 170.774초 |

Prometheus 규칙, Grafana의 PromQL 12개 및 규칙·Alertmanager 조회 API를 확인했다.
실제 발생·복구 HTTP POST가 실험용 수신기에 도착했다.
사용자의 Slack 등 외부 채널은 연결하지 않았다. 브라우저 육안 검수도 수행하지 않았다.

초기 Prometheus 설정 파일 권한 오류로 첫 약 14분의 관측 공백이 있었다.
오류를 보존하고 수정했으며, 이 공백을 포함해 연속 관측이 완벽했다고 주장하지 않는다.
최종 Prometheus 선택 지표의 원본 scrape 시각 데이터와 Grafana 대시보드 JSON을 회수했다.
전체 TSDB 백업은 아니다. 자세한 알림 조건과 제한은
[알림 검증 기록](PIPELINE_ALERTING_VERIFICATION.md)에 있다.

## 결과 보존과 리소스 정리

로컬 결과 위치:

`bigdata/reliability/.generated/ec2-runs/witw-rel-20261123-105044-35b97a/`

- `evidence.tar.gz`: 273,454,024 bytes. 입력·실제 출력·검증 결과·실험 로그 포함.
- `observability.tar.gz`: 224,068 bytes. Grafana 설정·조회 결과·선택 지표 이력 포함.
- `evidence/`, `observability/`: 위 압축 파일의 추출본.
- `host-cycles.json`: 외부 제어기에서 측정한 9회 결과.
- `integrity-verified.json`: 파일 388개 및 압축 파일 2개의 SHA-256 기록.
- `finish-status.json`: 결과 회수·검증 후 정리 완료 기록.

결과 검토 시 파일 388개와 압축 파일 2개의 해시를 다시 대조해 모두 일치했다.
해시는 증거 무결성 확인이며 시험 설계 자체의 타당성을 보증하는 것은 아니다.
원본 state에는 실험 DB 자격 증명이 있어 공개 포트폴리오에 그대로 올리지 않는다.

정리 코드는 EC2 terminate 완료를 AWS waiter로 확인한 후 실험 소유 VPC의 태그를 검사하고
서브넷·라우팅·보안 그룹·인터넷 게이트웨이·키페어·VPC를 삭제했다.
종료 당시 이 API 작업이 모두 성공했고 22:49:56 KST에 완료 상태를 기록했다.
다음 날 결과 검토 시 AWS 세션이 만료돼 현재 상태의 추가 조회는 수행하지 못했다.
실행 중 저장된 노드별 `running` 값은 마지막 기동 스냅샷이며 최종 정리 상태를 뜻하지 않는다.

## 포트폴리오에서 말할 수 있는 범위

> EC2 3대에서 Collector·Kafka·Spark·Backend의 장애 경계에 종료와 중단을 주입하고,
> 반복 대상 장애를 각각 3회 검증했다. 전송 전 종료에서 기존 버전의 3건 유실을 재현했고
> 영속 outbox 적용 버전에서는 유실이 없었다. 이벤트 순서 역전의 연결 오류 3,000건을
> 0건으로 줄였고, 노드별 stop/start 9회에서도 최종 데이터의 정확성을 확인했다.
> Prometheus와 Alertmanager를 통한 발생·복구 웹훅 수신도 검증했다.
> 다만 1만 건 처리 시험의 지연 증가가 관측돼 신뢰성과 처리 비용의 후속 분석이 필요하다.

단일 Kafka 브로커·RF1, Spark local 모드, 고정 NLP 결과의 제한된 구성이다.
다중 브로커 리더 선출, 분산 Spark worker 유실, HDFS 장애, EBS 소실,
실제 LLM 지연·요금, 장기 부하와 운영 SLA까지 검증한 결과로 확대하지 않는다.
